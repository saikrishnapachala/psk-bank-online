    Toyota Financial Services Bank Online: front end and BFF architecture

    The decisions, contracts and flows for rebuilding TFSB's online banking from scratch as a server-driven web app, with a mobile app to follow on the same screen definitions.

    ProductTFSB Online (web), TFSB mobile (future)
    Scope of this recordWeb front end, BFF, monorepo, auth, integrations seen from the BFF
    Out of scope (other teams)Java services, MuleSoft, Fiserv; the front-end team owns UI and BFF only
    ApproversEnterprise architect, security, compliance, front-end and backend leads

    Summary

    Server-driven UI. Every screen is a typed file in the monorepo, compiled to a versioned JSON template and served by a TypeScript BFF that fills in the customer's data. The Next.js web app renders it with a component catalog; the future mobile app renders the same JSON with native components.

    The browser talks to exactly three APIs: sign-in (OIDC), get a screen, and run an action. Everything else happens behind the BFF.

    The BFF owns experience, Java owns decisions. The BFF composes screens and calls Java services; Java decides everything about money and reaches Fiserv only through the MuleSoft API gateway.

    Tokens never reach the browser. The BFF is the OIDC client and keeps tokens server-side; the browser holds only a secure session cookie.

    Strong, layered MFA. Twilio Verify one-time codes for step-up; a phishing-resistant passkey or security key in addition for very high-value payments (proposed threshold: $20 million and above).

    One monorepo, separate deployables: the web app and the BFF are separate apps and separate Vercel projects, with a mobile placeholder and shared packages for the catalog, screens, tokens and runtime. Java, MuleSoft and Fiserv belong to other teams.

    Styling from one source: the designer owns the design tokens as JSON; the build generates the CSS; components use only semantic tokens, and the server never sends styles.

    Why server-driven UI

    Change screens with a BFF deploy only; one screen definition for web and mobile; consistency through a shared catalog.

    Why a BFF

    Keeps tokens and service topology out of the browser, shapes data per screen, and gives one place for security controls.

    Why it fits a bank

    Decisions stay server-side and audited; screens can be fixed or switched off instantly without app-store releases.

    Context and scope

    TFSB is rebuilding its existing online banking platform from scratch. The web experience ships first; a React Native mobile app follows and must reuse the same screens. Backend teams own Java domain services that integrate with Fiserv through MuleSoft. This record covers the front end and the BFF, and how they connect to everything else.

    Goals

    • One screen definition for web now and mobile later
    • Release screen changes without client releases
    • Bank-grade security, accessibility and auditability
    • Fast: cached navigation, server-rendered first load
    • A reference architecture other TFSB teams can reuse

    Non-goals

    • Business rules in the BFF or the browser
    • Business users editing screens without developers (screens are code)
    • Direct browser calls to Java, MuleSoft or Fiserv
    • Reusing code from earlier prototypes: the enterprise repository is the source

    Glossary

    TermMeaning here
    SDUIServer-driven UI: the server sends a description of the screen; the client draws it with its own components
    CatalogThe list of components and actions a screen may use, with their typed props; the contract between BFF and clients
    TemplateA screen's structure (which components, in what layout); the same for every customer, cacheable by hash
    DataThis customer's values for the screen (balances, names); short-lived and private
    ActionAnything the customer triggers: submit, confirm, load more; always a POST to the BFF
    JourneyA multi-step flow such as a wire transfer, tracked with a flow id
    Step-upExtra authentication requested in the middle of a session before a risky action

    The BFF contract: three APIs

    The browser and the future mobile app use only these. New features are new screens and actions, not new endpoints.

    APIRoutesPurposeKey rules
    1 · Auth (OIDC)GET /auth/login
    GET /auth/callback
    GET /auth/session
    POST /auth/logout    		Sign-in with the identity provider, session status, sign-outAuthorization code + PKCE; BFF is the confidential client; tokens stay server-side; browser gets a __Host- session cookie
    2 · ScreensGET /sdui/v1/screens/{screenId}Template + data for one screen, by id and parametersRead-only and idempotent; cacheable templates; data is private; per-section timeouts
    3 · ActionsPOST /sdui/v1/actions/{actionId}Every customer-triggered operationCSRF token required; Idempotency-Key required for money; schema-validated payload; returns an action result

    Headers the clients always send

    • X-TFSB-Client: web or ios/android later
    • X-TFSB-Catalog: catalog version the client can render
    • X-TFSB-Build: client build id (detects stale tabs)
    • Accept-Language: en-US, later es-US
    • X-Request-Id: generated per interaction, traced end to end

    What the BFF never does

    • Decide whether money can move, compute limits or fees
    • Call MuleSoft or Fiserv directly
    • Send tokens, full account numbers, styles or scripts to the browser
    • Trust a customer or account id that arrives from the browser
    • Store customer data beyond its session store and short caches

    Live balance updates: to stay within three APIs, phase 1 refreshes balances through the screens API (short cache plus refresh on focus and after money moves). Push updates (server-sent events) would be a fourth, read-only route; see ADR-011 and the open questions.

    How a page gets to the screen

    The full path for a signed-in customer opening /accounts for the first time in a session, with the time budget for each step. Later navigations skip most of it (cached template, client-side fetch of data only).

    Budget for the 75th percentile on mobile 4G: content visible within 2.5 s, interactive shortly after. Bars are to scale within the 2,500 ms budget.

    First load (server-rendered)

    • Next.js server component calls the BFF on the private side, so the HTML arrives with balances already in it
    • The renderer runs on the server for the first paint, then hydrates in the browser
    • The screen envelope is embedded in the page so the client cache starts warm, with no second fetch
    • Only the component chunks this screen uses are preloaded

    Later navigations (client-side)

    • Fresh in cache: the screen renders instantly, with no network call
    • Stale: shown at once from cache, then refreshed in the background
    • Template unchanged: the BFF sends data only
    • Next screen prefetched when its link is visible or hovered

    Where the screen JSON lives
    
  
    Screens change with releases, not daily, and there's no content management system. So screen definitions live in the monorepo, are reviewed like code, and are compiled into static, versioned JSON templates at build time. At request time the BFF only adds the customer's data.
    
  
    
    
    OptionHow it worksFit for TFSB
    
    
      
    A. Typed screen files in the monorepo, compiled to JSONScreens written with typed builders from the catalog in packages/screens; the build emits one JSON template per screen with a content hash; the BFF ships with themChosen Type-checked, reviewed, tested, versioned; perfect for AI-generated code; no runtime store to secure
    
      
    B. Hand-written JSON files in the monorepoSame location, but authored directly as JSON and validated by the catalog's JSON Schema in CIAcceptable Simpler to read; loses refactoring, autocomplete and compile-time errors
    
      
    C. Screens built in BFF code per requestLike the sdui-example: the BFF builds the tree on every requestNot preferred Works, but there's no static template to cache by hash or review as a file
    
      
    D. Database or content management systemScreens edited at runtime by business usersRejected Needs its own approvals, audit and testing; not needed when screens change with releases

    Authentication, sessions and MFA
    
  
    
    
    Sign-in (OIDC)
      
      
    • Authorization Code flow with PKCE (S256), state and nonce
      • 
      
    • BFF is a confidential client (private key JWT or mTLS client auth)
      • 
      
    • ID token validated: signature, issuer, audience, nonce, expiry
      • 
      
    • Access and refresh tokens encrypted in the BFF session store (Redis); never in the browser
      • 
      
    • Login MFA handled by the identity provider (Twilio-backed codes or passkeys)
      • 
    
    
    
    Session
      
      
    • Cookie __Host-tfsb_sid: HttpOnly; Secure; SameSite=Lax; Path=/, random 256-bit id
      • 
      
    • Idle timeout 10 minutes, warning at 8 minutes with "Stay signed in"; absolute limit 12 hours, then full sign-in (see the session table below)
      • 
      
    • Session id rotated after sign-in and after step-up
      • 
      
    • Sign-out revokes tokens at the IdP and clears the session everywhere; other tabs sign out too
      • 
      
    • CSRF token bound to the session, checked on every action, plus Origin check
      • 
    
    
  
    
  
    Step-up MFA levels
    
  
    
    
    LevelWhen (proposed)FactorsNIST 800-63B
    
    
      
    Sign-inEvery new session; risk-based on known devicesPassword + one-time code (Twilio Verify) or passkeyAAL2
    
      
    Step-upAdd or edit a payee; change contact details; transfers to others; wiresFresh one-time code by SMS, voice or email (Twilio Verify)AAL2
    
      
    High valuePayments of $20 million or more confirm thresholdTwilio one-time code and passkey or security key (WebAuthn, phishing-resistant); optional second approverAAL3-aligned
    
        
  
    
  
    Why a second factor type for high value: NIST 800-63B classes SMS codes as a restricted authenticator because SIM swaps and phishing can intercept them. A WebAuthn passkey or hardware key is bound to TFSB's domain, so a fake site can't use it. WebAuthn must run in the browser (navigator.credentials.get); the BFF relays the challenge and the signed assertion, and Java (or the IdP) verifies it.
    
  
    Session rules
    
  
    NIST 800-63B asks for re-authentication after 30 minutes of inactivity at AAL2 and 15 minutes at AAL3, and at least every 12 hours. Online banks commonly go stricter on idle time. Recommended:
    
  
    
    
    RuleValueEnforced by
    
    
      
    Idle timeout10 minutes; warning dialog at 8 minutes; activity in any tab keeps all tabs aliveBFF session (authoritative) + app shell timer (warning only)
    
      
    Absolute session lifetime12 hours, then full sign-in with MFABFF session
    
      
    Step-up freshnessAn MFA result is valid for 5 minutes and for one specific transactionJava
    
      
    High-value freshnessFresh factors for every high-value payment, regardless of recent MFAJava
    
      
    Sensitive profile changesPhone, email, address, password, MFA devices: step-up plus a notification to the old contact detailsJava
    
      
    Concurrent sessionsAllowed, listed in Security settings, each revocable; new-device sign-ins notifiedBFF + IdP
    
      
    Sign-outRevokes tokens at the IdP, deletes the session, clears all client caches in every tabBFF + runtime
    
      
    Session idRotated at sign-in and after each step-up; never in URLs or logsBFF
    
        
  
    
  
    High-value payments and fraud controls (required)
    
  
    
    
    Controls on large payments
      
      
    • Threshold: $20 million and above triggers the high-value path (value owned by risk and compliance, held in Java configuration)
      • 
      
    • Two different factor types: Twilio one-time code and a passkey or security key
      • 
      
    • Transaction signing: the passkey challenge is derived from the payment details (amount, payee, account), so the signature covers exactly what the customer saw
      • 
      
    • Second approver for business accounts (dual control), each with their own MFA
      • 
      
    • Review queue: Java can hold a payment for fraud review; the receipt says "pending review", never "sent"
      • 
      
    • Call-back for a first large wire to a new payee, as set by fraud operations
      • 
    
    
    
    Fraud signals the front end provides
      
      
    • Device and behavior intelligence: a fraud vendor's browser SDK (vendor to be chosen) collects device and interaction signals; only its session id goes to Java with each risky action
      • 
      
    • New payee cooling-off: limits on the first payments to a new payee, shown clearly in the UI
      • 
      
    • Velocity limits: per-customer transfer counts and amounts, enforced in Java, explained in the UI
      • 
      
    • Notifications: email/SMS/push for new payees, large payments, contact changes and new devices
      • 
      
    • Scam warnings: Java can attach a warning (for example "Did someone ask you to send this?") that the review screen must show and the customer must acknowledge
      • 
      
    • Never weaken controls in the UI: if Twilio or the passkey service is down, high-value payments wait
      •

    Front-end design
    
  
    Where logic lives: four tiers
    
  
    
    
    Tier 1 In the screen JSON
    Bindings, lists, show/hide, simple checks (required, length). Declarative only, never formulas.
    
    
    Tier 2 Named functions in web code
    Referenced by name: routingNumber check, usd format, business-day calendar with Fed holidays.
    
    
    Tier 3 Journey widgets
    TransferForm, PayeePicker, OtpInput, PasskeyPrompt, PlaidLink: full components the BFF configures.
    
    
    Tier 4 Java only
    Eligibility, limits, fees, MFA requirement, approvals, posting. Never in the browser or the BFF.

    Styling: the decision and why
    
  
    Eight realistic options, scored for this product: a server-driven bank UI, built largely with AI assistance, by several teams, with web now and React Native later. More squares is better.
    
  
    
    
    OptionConsistency with tokensRuntime costServer componentsAI-assisted codingPath to React NativeVerdict
    
    
  
    
  
    How each approach works, and what it means for us
    
  
    
    
    ApproachHow it worksStrengthsWeak spots for a bank with its own brand
    
    
      
    CSS Modules + tokens (chosen)One .module.css file per component; Next.js scopes class names at build time; values come from token CSS variablesZero runtime, built into Next.js, works with server components, plain CSS anyone can read, easy to lint to tokens onlySlightly more files; variants written as data attributes rather than props
    
      
    Plain global CSSStylesheets loaded globally; naming conventions (BEM) avoid clashesSimplest possible, no toolingNothing enforces scoping; with several teams, overrides and dead CSS pile up
    
      
    Sass / SCSSPreprocessor: variables, nesting, mixins, compiled to CSSMature, familiar, mixins for repeated patternsSass variables are build-time only, so they can't theme at runtime; modern CSS covers nesting and variables natively
    
      
    LessOlder preprocessor, similar to SassFamiliar to some teamsShrinking community and tooling; no reason to start a new product on it
    
      
    Tailwind CSSUtility classes in markup; config or @theme maps to tokensFast to write, small CSS output, popular with AI toolsLong class lists are hard to review against design specs; arbitrary values (bg-[#f00]) bypass the brand unless extra lint is added; doesn't carry to React Native without another layer
    
      
    vanilla-extractStyles written in TypeScript, compiled to static CSSType-safe tokens, zero runtimeExtra build setup, smaller community, harder for designers to read
    
      
    Runtime CSS-in-JS (styled-components, Emotion)Styles created in JavaScript at runtimeDynamic styling, co-located with componentsDoesn't fit React Server Components; runtime cost on every page; styled-components is in maintenance mode
    
      
    Restyled library (MUI, Chakra, Bootstrap)Ready-made components, themed to the brandFastest first screensWe'd spend effort overriding someone else's design; their markup and behaviour become our accessibility risk
    
        
  
    
  
    
    
    Why CSS Modules is the best pick for us
      
      
    • SDUI means only the catalog has CSS. About 40 to 60 components, each with one small file. Screens are JSON and never carry styles.
      • 
      
    • Custom brand from our designer. We style against our tokens, not a framework's scale, so a framework adds nothing.
      • 
      
    • Strict and auditable. Stylelint allows only token variables. An off-brand colour fails CI.
      • 
      
    • Zero runtime, server-component friendly, built into Next.js. No extra dependency to approve or upgrade.
      • 
      
    • Mobile ready. The same tokens generate tokens.ts for React Native.
      • 
      
    • Plain CSS skills. Any developer, reviewer or AI agent can read it; nothing to unlearn in five years.
      • 
    
    
    
    Do we still need Sass or Less?
      
      
    • No. Modern CSS covers what they gave us: custom properties (runtime theming), native nesting, color-mix(), @layer, container queries.
      • 
      
    • Next.js already compiles CSS with modern tooling, so there's no preprocessor to add.
      • 
      
    • If a team ever needs mixins, Sass can be enabled per file inside CSS Modules (.module.scss) without changing anything else. It's reversible, so it isn't a risk.
      • 
      
    • Less is not recommended for a new product.
      • 
    
    
  
    
  
    
    
    Decision: tokens + CSS Modules
      
      
    • Design tokens are the single source: compiled to CSS variables for web and TypeScript constants for React Native
      • 
      
    • One .module.css per catalog component; scoped class names; zero runtime
      • 
      
    • Stylelint rules reject raw hex colors, pixel font sizes, ad-hoc z-index and spacing outside the scale
      • 
      
    • Layout comes from catalog components (Grid, Columns, Stack, ShowAt), never from per-screen CSS
      • 
      
    • Container queries inside components, so a card adapts to its column, not just the window
      • 
    
    
    
    How CSS stays manageable at scale
      
      
    • Cascade layers: @layer reset, tokens, base, components, utilities, so order never surprises anyone
      • 
      
    • Only the registry has CSS. Screens have none, because screens are JSON
      • 
      
    • Themes and brands switch by changing token values under [data-theme]; components don't change
      • 
      
    • Visual regression screenshots of every component state in light and dark on every pull request
      • 
      
    • AI guardrail: the steering file tells the agent to use tokens and the lint rules fail any build that doesn't
      •

    Design tokens: the designer owns them, the build turns them into CSS
    
  
    The UX designer keeps every style value (colors, type, spacing, radius, shadows, motion) as JSON. Nobody writes those values by hand in CSS. A build step turns the JSON into CSS variables for the web and TypeScript constants for React Native, and CI checks every change before it can merge.
    
  
    
    
    
      
    1 · FigmaDesigner edits native Figma Variables (no paid plugin)
    
      
    2 · ExportFigma's built-in DTCG export (or pnpm tokens:pull on Figma Enterprise) writes JSON into packages/tokens/src
    
      
    3 · Pull requestOpened by the designer; designer + front-end lead are required reviewers
    
      
    4 · ValidateFormat, naming, references resolve, no duplicates
    
      
    5 · AccessibilityEvery text/background pair checked for WCAG contrast in light and dark
    
      
    6 · BuildStyle Dictionary emits CSS variables, TypeScript, docs
    
      
    7 · Visual diffStorybook screenshots of every component, before and after

    Rules that keep CSS from getting confusing
    
  
    
    
      
      
    • Only components have CSS. Screens are JSON and have none. Pages never get custom styles.
      • 
      
    • Components use semantic tokens only. Never a primitive (--color-red-600) and never a raw value; Stylelint fails the build.
      • 
      
    • One CSS Module per component, next to it, same name. No global classes except the reset and tokens.
      • 
      
    • Variants are attributes, not classes: data-tone, data-size, data-state, matching catalog props one-to-one.
      • 
      
    • Cascade layers in a fixed order: reset, tokens, base, components, utilities. Specificity fights can't happen.
      • 
    
    
    
      
      
    • Logical properties only (margin-inline, inset-block), so right-to-left works later.
      • 
      
    • rem for type and spacing, so text zoom to 200% works; px only for hairlines.
      • 
      
    • No !important, no z-index numbers: layering uses named tokens (--z-overlay, --z-toast).
      • 
      
    • Motion and contrast respect the user: prefers-reduced-motion and forced-colors handled in every interactive component.
      • 
      
    • A design change is a token change. If a design can't be expressed in tokens and catalog props, it goes to the catalog review, not into a one-off style.
      • 
    
    
  
    

  
    Future scenarios this handles without rework

    Why this choice won't be a regret: every visual value lives in one designer-owned source, every component reads it the same way, and the server never sends styles. If CSS tooling changes in five years, only the component style files change; tokens, catalog, screens and the BFF don't. That is the cheapest possible exit, which is what makes it safe to commit now.
    

    


    
  
    
  
    Code splitting and bundle strategy
    
  
    In server-driven UI the browser doesn't know in advance which components a screen needs, so splitting is driven by the catalog: each component is its own chunk, and the BFF tells the client which ones a screen uses.

    FrameworkReact, Next.js runtimeEvery page, long-cached~ 90 KB
    
      
    App shellHeader, navigation, idle-timeout dialog, error boundaries, toastsEvery page≤ 25 KB
    
      
    Runtime + rendererScreen fetch, cache, action pipeline, challenge handling, renderer adapterEvery page≤ 35 KB
    
      
    Core componentsText, Heading, Money, Stack, Grid, Card, Button, SkeletonEvery page (used everywhere)≤ 20 KB
    
      
    Feature componentsAccountCard, TransactionList, AmountField, DatePicker…Only when a screen uses them≤ 15 KB each
    
      
    Journey widgetsWireForm, OtpInput, PasskeyPromptOnly when the journey starts≤ 25 KB each

    No waterfalls
      
      
    • Each screen envelope lists the component types it uses: "uses": ["BalanceHero", "AccountCard"]
      • 
      
    • On the server, Next.js adds preload links for exactly those chunks to the first HTML
      • 
      
    • On client navigation, the runtime starts loading chunks in parallel with the data request
      • 
      
    • After the page is idle, chunks for the likely next screens are prefetched
      • 
      
    • Every lazy component has a skeleton the same size as the real thing, so nothing jumps
      • 
      
    • CI fails a pull request that breaks a budget; bundle analysis is attached to every preview

    Do we need GraphQL in the BFF?
    
  
    No. The BFF already returns exactly what each screen needs, and the browser only ever calls three endpoints. GraphQL solves a problem this design doesn't have.
    
  
    
    
    WhereGraphQL?Reason
    
    
      
    Browser → BFFNoScreens are composed server-side; clients don't choose fields. A query language would let clients ask for data the screen doesn't need and widen the attack surface
    
      
    BFF → JavaNoJava teams publish REST with OpenAPI; the BFF calls a handful of task endpoints in parallel
    
      
    Money actionsNoExplicit endpoints with idempotency keys, step-up and audit are clearer than mutations
    
      
    Later, if many teams build many BFFsMaybeA federated GraphQL layer in front of Java read APIs could help; revisit only then

    Appendix: server-driven UI or React Server Components?
    
  
    The question the architecture review will ask: "Next.js already renders on the server. Why not just use React Server Components and skip server-driven UI?" This appendix gives the full comparison so the team can decide with data.
    

  
    First, they're not the same kind of thing
    
  
    
    
    TechniqueQuestion it answersWhat travels to the clientPlatformsTypical use
    
    
      
    SSR server-side renderingWhere is the first HTML produced?HTML per request, then hydrationWebPersonalized pages that must appear fast
    
      
    SSG static generationCan the page be built once?Prebuilt HTML from a CDNWebMarketing, help, rates
    
      
    ISR incremental regenerationCan a static page refresh itself?Prebuilt HTML, rebuilt on a schedule or on demandWebPublic content that changes sometimes
    
      
    RSC React Server ComponentsWhich components run only on the server?A serialized React tree (RSC payload), streamedWeb; React Native support experimentalLess browser JavaScript, server-side data fetching
    
      
    SDUI server-driven UIWho decides what is on the screen, for every platform?Versioned JSON from a component catalogWeb and nativeOne screen definition across channels, changes without app releases
    
        
  
    
  
    The key point: RSC and SSR are rendering techniques for the web client. SDUI is a contract between the server and every client. They stack: SDUI decides what the screen is; RSC and SSR decide how the web draws it quickly. TFSB's design uses both.
    

  
    
    
    
      
    Option A RSC only
    Screens written as React components in the Next.js app. Server components call the BFF (or Java via the BFF) directly. A future mobile app builds its own screens.
    
      
    Option B SDUI + RSC (proposed)
    Screens as typed files compiled to JSON templates. Next.js renders them with RSC/SSR for fast first loads. React Native renders the same JSON later.
    
      
    Option C RSC now, SDUI later
    Ship web with RSC only; introduce SDUI when mobile starts, migrating existing screens to the catalog.

    The honest case for RSC only
    
  
    
    
    When A is the right answer
      
      
    • Mobile is cancelled, or more than two to three years away
      • 
      
    • Mobile would be a different product with different screens
      • 
      
    • The team can't staff a platform group for the catalog and renderer
      • 
      
    • The first release date is fixed and close
      • 
    
    
    
    What A costs later if mobile does arrive
      
      
    • Every journey rebuilt in React Native, then kept in sync by hand
      • 
      
    • Two sets of tests, accessibility reviews and disclosure checks
      • 
      
    • Or a migration to SDUI (Option C), rewriting web screens into catalog templates

    My recommendation for TFSB
    
  
    
    
    Choose B: SDUI + RSC, because mobile is on the roadmap and a bank needs to fix wording, warnings and broken flows on every channel the same day, with one auditable definition of what customers saw.
    
    
    Use RSC for what it's best at: server-rendering the SDUI screens on first load, the app shell, and public pages (with SSG/ISR for marketing and help).
    
    
    Add a checkpoint: if the mobile app is cancelled or pushed out beyond three years, switch to Option A and drop the SDUI platform work. The two-to-three-week spike is the moment to confirm.
    
  
    

  
    Talking points for the review
    
  
    
    
    If someone asks…Answer
    
    
      
    "Isn't RSC already server-driven UI?"For the web, partly: the server sends the UI tree. But it's React's internal format, tied to one deployment, and it doesn't serve native mobile apps today. SDUI is a stable, versioned contract for every client.
    
      
    "Isn't SDUI over-engineering?"For a web-only app, yes. With mobile planned, it's what stops us building every banking journey twice.
    
      
    "Will SDUI make the web slower?"Slightly more JavaScript (renderer and registry), offset by catalog-driven code splitting and RSC on first load. Both options meet the 2.5 s target.
    
      
    "Can't React Native use Server Components?"Expo has experimental support. It's not something to bet a bank's mobile app on yet, and it still wouldn't give versioned fallbacks for old app installs.
    
      
    "What do we lose?"Design freedom outside the catalog, and time to build the platform. We accept that for consistency, auditability and mobile reuse.
    
      
    "What if we're wrong?"Templates are plain JSON and components are plain React, so moving to RSC-only later means writing screens as components; the components and BFF carry over.
